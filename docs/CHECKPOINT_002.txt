Known limitations:
  - Evaluates one question's gap signals at a time. No questionnaire-level
    aggregation or scoring (intentionally out of scope).
  - Semantic conditions are detected and surfaced but not evaluated; that is
    the future semantic evaluator's responsibility.
  - Negative tests requiring malformed/missing knowledge use isolated in-memory
    fixtures; production knowledge is never corrupted to test failure paths.
  - No API, no persistence, no LLM, no UI.

Hardening (post-review patch, Checkpoint 002 scope only):
  1. Semantic reference integrity. KnowledgeBase now loads semantic_condition
     records read-only from knowledge/soc2/semantics/. When a gap signal carries
     a semantic_condition_id, the semantic-boundary path resolves it via
     require_semantic_condition(); an unknown ID raises KnowledgeError. The
     semantic condition is resolved, never evaluated. Semantic records unchanged.
  2. Duplicate runtime IDs. KnowledgeBase.from_repository() explicitly detects
     duplicate questionnaire, finding, and semantic-condition IDs across files
     and raises KnowledgeError naming the duplicated ID, instead of letting dict
     overwrite or set de-duplication hide the collision.
  3. Grammar-version compatibility. Before deterministic evaluation the engine
     checks the questionnaire's declared gap_signal_grammar_version against the
     supported version (1.0.0). A different or missing version raises the typed
     UnsupportedGrammarVersionError (subclass of EngineError) rather than
     attempting evaluation.
